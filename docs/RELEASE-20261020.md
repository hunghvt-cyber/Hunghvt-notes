## Foreground priority and quieter recovery UI

User requested reducing background load to prioritize opening/saving, and simplifying
visible device-draft UI. Follow-up changes:

- One per-tab HTTP lane prioritizes queued writes, foreground reads, then optional
  background reads. It never aborts an already dispatched write. Retry waiting is
  outside the lane so it does not block another foreground action.
- Identical concurrent GETs within the same foreground/background context share a
  promise. This is in-flight coalescing only, not an authorization/content cache.
- Optional background refresh is skipped while hidden/offline or while foreground,
  editing/delivery or organization work is active. Background reads make a single
  attempt rather than start a two-minute retry chain. Periodic refresh is nonoverlapping
  and jittered at 60–70 seconds after each completed tick; background ticks do not add
  trailing full-refresh requests while another refresh runs.
- Shared links retain periodic/visibility authorization checks. During editing or
  foreground work, accessOnly reads validate live capability/scope/membership under
  one lease and return permission only, without reading immutable content. Foreground
  read/write ACL checks remain unchanged. Busy/network failures do not count as a
  successful authorization check or trigger a background retry storm.
- Stale open responses do not replace a newer editor choice. Background refresh does
  not repaint a dirty shared editor unless its permission changed to read-only.
- Normal status text is short: Đang lưu / Đã lưu / Chưa đồng bộ. The recovery panel no
  longer opens automatically; its button hides when empty. Existing draft records,
  frozen operations, export and conflict recovery are preserved. No draft deletion,
  storage migration or false cloud-save acknowledgement was introduced.

Validation performed: JavaScript syntax checks and diff review only. Browser selectors
were adjusted for the intentional recovery-panel labels/default collapsed behavior.
No manual load or browser test run, per user direction; existing automatic CI remains.
These client scheduling changes do not remove cross-instance root-lock contention,
guarantee live throughput, or interrupt an already running background request.

## Permanent trash deletion

User requested a permanent-delete control next to Restore selected. Added owner-only
Xóa vĩnh viễn đã chọn, disabled until there is a selection, with a count-specific
irreversible confirmation. Existing drafts for selected IDs block the UI action rather
than being silently deleted. Adding/deploying the feature never invokes it on user data.

Backend purge requires owner authentication, same-origin JSON POST, note UUID, exact
trash revision and an operation UUID. It rejects live/restored notes. Before any file
DELETE it publishes and verifies a durable purge journal and revokes individual links.
It inventories only the configured namespace at Depth 1, accepts only exact immutable
record basenames for that note (including its legacy fixture slot when applicable),
and validates the filename allowlist again immediately before deletion.

Cleanup processes at most five files per root lease, using inherited-token DELETE and
GET-404 verification. Journal progress is committed/verified between batches. Failed
or uncertain calls leave the trash row marked as deleting; retry uses its same operation
UUID. Restore/preview are blocked once purge begins. UI performs bounded batches and
reports incomplete cleanup instead of claiming success. On completion, remove the entry
and custom-order reference and retain a small ID/operation marker to reject delayed
creation/replay resurrection. Existing frozen draft safety is unchanged.

Backup export rejects an in-progress purge rather than exporting partially removed
records. A later backup excludes the erased entry and preserves erased-ID markers when
restoring. Previously downloaded backups and Koofr's own retention are outside this
control; this is permanent deletion from Notes, not a secure-erasure guarantee for copies.

Validation: syntax checks and diff review only, following the user's instruction not
to continue manual testing. No deletion test or delete call on production data was run.
Provider behavior is not newly live-qualified; failures remain resumable/unconfirmed.
